## 输出长度控制的可行性结论

官方 [Chat Completions 文档](https://api-docs.deepseek.com/api/create-chat-completion/)说明 `max_tokens` 是输出上限；本次核查未发现公开的 `min_tokens` 或 `ignore_eos` 参数。没有据此直接断言所有实现都不支持，而是针对本次固定路由 `https://api.deepseek.com/v1/chat/completions`、模型 `deepseek-flash` 做了独立有界反例验证：

| 探针 | 新增字段 | max_tokens | HTTP | 实际输出 | 结束原因 |
| --- | --- | ---: | ---: | ---: | --- |
| 默认对照 | 无 | 64 | 200 | 1 | stop |
| 最小长度 | `min_tokens=64` | 64 | 200 | 1 | stop |
| 忽略 EOS | `ignore_eos=true` | 64 | 200 | 1 | stop |

三者使用相同短提示词、非思考模式、温度 0，各发一次；响应均为 `OK`，usage 输出为 1 token。这证明：**在当前被测路由中，HTTP 接受这两个字段仍不能保证生成到 64 token。** 参数是否在内部被忽略未作内部观测，不能仅凭 HTTP 200 判定有效。即便某次刚好生成 64 token，也不足以证明存在长度保证。原始请求没有加入这些未公开字段，探针未混入正式统计，没有追加提示词、续写或补发请求凑长度。

| 会话 | 实际输出 / 原始保存的输出长度 | 覆盖比例 |
| --- | ---: | ---: |
| 主流区间重叠样本 | 6,400 / 6,409 | 99.86% |
| 单子代理 | 3,568 / 3,949 | 90.35% |
| 多子代理 | 14,937 / 231,817 | 6.44% |
| 原始区间串行 | 4,266 / 4,266 | 100.00% |
| 长上下文 | 15,988 / 25,393 | 62.96% |

原始 `out` 是保存的输出长度，本实验把它转成新请求的 `max_tokens` 上限，不能保证原始生成负载被重现。多子代理的大输出缺口保留为明确限制；单纯增加会话数或增加上限不能消除这个已观察到的问题。正式测量反映“固定合成输入 + 当前模型实际生成”，业务工具和原始业务成功率未复现。新模型生成结果没有反馈到后续固定输入。
